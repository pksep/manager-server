# Запуск ВКонтакте и Авито в СЭП Чате

Этот документ нужен для вывода уже реализованных интеграций ВКонтакте и Авито в
рабочее окружение. После запуска новые сообщения из площадок появляются в СЭП Чате
→ «Клиенты», а ответ менеджера возвращается в тот же канал. Сервис не переносит
старую переписку и не импортирует ответы, написанные непосредственно в интерфейсе
площадки.

Документ относится к `manager-server`, ветке `manager`, ревизии
`c1318ec9a1bd9d438ed25a29af2eed3e3558593b`.

## Что необходимо развернуть

1. Обновить `manager-server` до указанной ревизии и применить его миграции до
   запуска приложения.
2. Обновить `chat-server` до поставки с разделом «Клиенты» и применить его
   миграцию `20260915160000-manager-channels`; обновить `chat-client` той же
   поставки. Для доступа менеджеров настроить в `chat-server` источник ролей ERP
   из следующего раздела.
3. Развернуть совместимые изменения ERP-клиента и ERP-сервера: право
   `chat.clients:view` даёт доступ к разделу «Клиенты», а синхронизация контакта
   использует внутренний API ERP.
4. Предоставить manager-server сетевой доступ к PostgreSQL, Redis, RabbitMQ,
   ClamAV, внутреннему API СЭП Чата, внутреннему API ERP и исходящий HTTPS к
   `api.vk.com`, `api.avito.ru`, CDN вложений ВКонтакте и Авито, Яндекс
   SmartCaptcha.
5. Предоставить `chat-server` внутренний HTTPS-доступ к ERP. Именно
   `chat-server`, а не `manager-server`, каждые 5 секунд получает из ERP
   сотрудников с правом «Чат → Клиенты → Полный доступ».

`manager-server` не имеет публичного порта. В интернет публикуется только
входной шлюз с HTTPS; сам сервис слушает внутренний порт `4314`.

## Секреты и переменные окружения

Секреты хранятся только в Vault/Kubernetes Secret или эквивалентном закрытом
хранилище. Не добавлять их в Git, ConfigMap, URL, журналы CI, трассировки и
сообщения об ошибках. Все новые секреты должны быть независимыми случайными
значениями. Для webhook-секретов допустимы только символы `A–Z`, `a–z`, `0–9`,
`_`, `-`; длина от 32 до 128 символов.

| Переменная                                   | Кто задаёт            | Требование                                                                                                      |
| -------------------------------------------- | --------------------- | --------------------------------------------------------------------------------------------------------------- |
| `HOST`                                       | DevOps                | `0.0.0.0` внутри закрытой сети контейнеров.                                                                     |
| `PORT`                                       | DevOps                | `4314`, не публиковать напрямую.                                                                                |
| `DATABASE_URL`                               | DevOps                | Строка подключения runtime-роли manager. Только DML-права: SELECT/INSERT/UPDATE/DELETE и sequences.             |
| `MANAGER_MIGRATION_DATABASE_URL`             | DevOps                | Отдельная миграционная роль; используется только для `bun run migrate:up`.                                      |
| `MANAGER_INTERNAL_KEY`                       | DevOps                | Новый случайный секрет не короче 32 символов.                                                                   |
| `CHAT_SERVICE_URL`                           | DevOps                | Внутренний HTTPS URL СЭП Чата, включая `/api`.                                                                  |
| `CHAT_MANAGER_KEY`                           | DevOps + команда Чата | Согласованный отдельный секрет не короче 32 символов для manager-server → СЭП Чат.                              |
| `ERP_SERVICE_URL`                            | DevOps                | Внутренний HTTPS URL ERP, включая `/api`. Указывается вместе с `ERP_MANAGER_KEY`.                               |
| `ERP_MANAGER_KEY`                            | DevOps + команда ERP  | Отдельный секрет не короче 32 символов для manager-server → ERP.                                                |
| `MANAGER_SITES_PATH`                         | DevOps                | Путь к рабочей конфигурации сайтов виджета, не к `config/sites.example.json`.                                   |
| `MANAGER_CHANNELS_PATH`                      | DevOps                | Абсолютный путь к конфигурации подключений из раздела ниже.                                                     |
| `MANAGER_PUBLIC_URL`                         | DevOps                | Публичный HTTPS origin без пути, например `https://manager.example.ru`. Нужен для регистрации webhook Авито.    |
| `REDIS_URL`                                  | DevOps                | Закрытое подключение к выделенной DB Redis. В production использовать TLS при выходе за доверенную сеть.        |
| `MANAGER_RABBITMQ_URL`                       | DevOps                | Закрытое подключение к отдельному vhost RabbitMQ. Обязательно: без брокера сервис не готов принимать обращения. |
| `MANAGER_QUEUE_PREFIX`                       | DevOps                | Уникальный префикс очередей данного окружения, например `manager-prod`.                                         |
| `MANAGER_REDIS_PREFIX`                       | DevOps                | Уникальный префикс счётчиков данного окружения, например `manager:security:prod`.                               |
| `MANAGER_TRUSTED_PROXIES`                    | DevOps                | Точные CIDR или IP входных прокси через запятую. Не использовать `0.0.0.0/0`.                                   |
| `MANAGER_CAPTCHA_MODE`                       | DevOps                | `adaptive` для сайта; `disabled` допустим только на loopback-стенде.                                            |
| `SMARTCAPTCHA_CLIENT_KEY`                    | DevOps                | Клиентский ключ Яндекс SmartCaptcha.                                                                            |
| `SMARTCAPTCHA_SERVER_KEY`                    | DevOps                | Серверный ключ Яндекс SmartCaptcha.                                                                             |
| `MANAGER_SCAN_MODE`                          | DevOps                | `required`.                                                                                                     |
| `MANAGER_CLAMAV_HOST`, `MANAGER_CLAMAV_PORT` | DevOps                | Закрытый доступ к здоровому ClamAV.                                                                             |
| `VK_BUSINESS_URL`                            | DevOps/бизнес         | Необязательно. HTTPS-ссылка на сообщество ВК; выводится в popover виджета как «Написать ВКонтакте».             |

Рекомендуемые рабочие значения квот уже заданы приложением. Не менять их на первом
запуске без отдельного решения: `MANAGER_QUEUE_LIMIT=10000`,
`MANAGER_WORKER_MS=1000`, `MANAGER_UPLOAD_BYTES=20971520`.

## Доступ менеджеров к разделу «Клиенты»

Права для меню и API раздела проверяет **chat-server**. Одна только выдача
права в ERP не выводит кнопку в Чате: chat-server должен получить актуальный
снимок ролей ERP. Если снимка нет либо срок его действия истёк, `GET
/api/manager/access` возвращает `{ "allowed": false }`, и клиент Чата скрывает
пункт «Клиенты» полностью.

В Secret развёртывания **chat-server** добавить следующие значения:

| Переменная | Значение |
| --- | --- |
| `MANAGER_ERP_ACCESS_URL` | Полный внутренний HTTPS URL `https://<erp-host>/api/internal/manager/access`. |
| `MANAGER_ERP_ACCESS_KEY` | В точности значение `ERP_MANAGER_KEY` соответствующего ERP-окружения. |
| `MANAGER_SERVICE_URL` | Внутренний HTTPS URL `manager-server`, без публичного gateway. Нужен для карточки клиента, заметок, менеджеров и синхронизации контактов. |
| `MANAGER_INTERNAL_KEY` | В точности значение `MANAGER_INTERNAL_KEY` развёртывания manager-server. |
| `CHAT_MANAGER_KEY` | В точности значение `CHAT_MANAGER_KEY` развёртывания manager-server. |

После изменения Secret перезапустить chat-server. Затем он запрашивает ERP каждые
5 секунд; снимок действует 30 секунд и не продлевается при ошибке ERP, сети или
ключа. В журналах chat-server не должно быть сообщения «Не удалось обновить
права клиентов из ЕРП».

Проверить до выдачи роли, что установлены совместимые образы: chat-server и
ERP-server должны содержать поставку manager из `canary`; стабильные ветки,
которые не содержат модуль manager, не создают маршрут доступа и не могут
показать раздел. После установки права проверить три условия:

1. В ERP у сотрудника есть «Чат → Клиенты → Полный доступ» (`chat.clients:view`)
   и применена миграция `20260915120000-manager-client-permission`.
2. Табель сотрудника в ERP совпадает с `nickname` его пользователя СЭП Чата.
   Пользователь должен уже существовать в Чате после штатной синхронизации.
3. После ожидания до 10 секунд открыть Чат заново или обновить вкладку. В
   браузерной сети `GET /api/manager/access` должен вернуть
   `{ "allowed": true }`.

Для изолированной проверки источника DevOps может выполнить из контейнера
chat-server, не выводя ключ в консоль или логи:

```bash
curl --fail --silent --show-error \
  -H "x-manager-key: $MANAGER_ERP_ACCESS_KEY" \
  "$MANAGER_ERP_ACCESS_URL"
```

Ответ должен содержать в `actors` табель выданного менеджера. HTTP 401/403
означает несовпадение ключей, HTTP 404 - неподходящую ревизию ERP-server, а пустой
`actors` - отсутствие права, блокировку роли/сотрудника или несовпадение данных
роли. Если ERP возвращает табель, но пользователь всё равно не появляется в
снимке chat-server, сверить `actors[].tabel` с `users.nickname` в базе Чата.

## Конфигурация каналов

Создать файл, доступный контейнеру только для чтения, например
`/etc/manager/channels.production.json`, и указать его в
`MANAGER_CHANNELS_PATH`. В JSON находятся только ID и имена переменных; реальные
ключи остаются в Secret.

Заменить все значения в угловых скобках. В первом развёртывании оставить оба
`enabled` равными `false`, проверить готовность инфраструктуры, затем включать
площадки по одной.

```json
[
  {
    "id": "vk-company",
    "platform": "vk",
    "name": "<отображаемое название сообщества>",
    "accountId": "<числовой ID сообщества без знака минус>",
    "enabled": false,
    "webhookSecretEnv": "MANAGER_VK_WEBHOOK_SECRET",
    "tokenEnv": "MANAGER_VK_TOKEN",
    "confirmationEnv": "MANAGER_VK_CONFIRMATION"
  },
  {
    "id": "avito-company",
    "platform": "avito",
    "name": "<отображаемое название аккаунта>",
    "accountId": "<числовой ID основного аккаунта Авито>",
    "enabled": false,
    "webhookSecretEnv": "MANAGER_AVITO_WEBHOOK_SECRET",
    "clientIdEnv": "MANAGER_AVITO_CLIENT_ID",
    "clientSecretEnv": "MANAGER_AVITO_CLIENT_SECRET"
  }
]
```

Секреты для этого файла:

```dotenv
# ВКонтакте: токен сообщества с правами сообщений, пользователей и документов.
MANAGER_VK_TOKEN=<токен сообщества ВКонтакте>
MANAGER_VK_CONFIRMATION=<строка подтверждения из Callback API ВКонтакте>
MANAGER_VK_WEBHOOK_SECRET=<уникальная случайная строка 32–128 допустимых символов>

# Авито: OAuth credentials основного корпоративного аккаунта, не сотрудника.
MANAGER_AVITO_CLIENT_ID=<client_id Авито>
MANAGER_AVITO_CLIENT_SECRET=<client_secret Авито>
MANAGER_AVITO_WEBHOOK_SECRET=<другая уникальная случайная строка 32–128 допустимых символов>
```

`id`, `platform` и `accountId` существующего подключения менять нельзя: для другого
аккаунта необходимо создать новую запись с новым `id`. Отключение подключения
сохраняет историю, но запрещает новые приём и ответы.

## База данных и запуск сервиса

До запуска HTTP-процесса выполнить миграцию отдельно от runtime-роли:

```bash
bun run migrate:up
bun run migrate:status
```

Для новой базы применить разграничение прав из
`config/database-permissions.sql`, подставив реальные имена миграционной и runtime
ролей. Runtime-роль не должна иметь права `CREATE`, быть владельцем схемы или
superuser. Автоматических миграций при старте HTTP-сервиса нет.

После запуска проверить с внутренней сети контейнеров или с allowlist-пробы
балансировщика:

```bash
curl --fail --silent --show-error http://manager-server:4314/health/live
curl --fail --silent --show-error http://manager-server:4314/health/ready
```

`/health/ready` должен вернуть HTTP 200. При недоступности Redis, RabbitMQ или базы
он не должен считаться готовым, а виджет не должен отображаться.

## Входной шлюз и HTTPS

Взять [config/nginx.conf](../config/nginx.conf) за основу и заменить пример
`10.20.0.0/24` точными адресами балансировщика. TLS завершается до этого nginx;
балансировщик обязан **перезаписывать**, а не дописывать входящий
`X-Forwarded-For`.

Публично разрешить только следующие пути:

| Путь                                        | Назначение           | Условие                                                                                                                 |
| ------------------------------------------- | -------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `/v1/widget/*`                              | Виджет сайта         | Обычные rate limits, WebSocket upgrade.                                                                                 |
| `/v1/channels/vk/vk-company`                | Callback ВКонтакте   | Тело до 256 KiB, короткий таймаут.                                                                                      |
| `/v1/channels/avito/avito-company/<секрет>` | Callback Авито       | Тело до 256 KiB, HTTP 200 за 2 секунды.                                                                                 |
| `/health/live`, `/health/ready`             | Проверка доступности | Не публикуются в шаблоне nginx. Проверять по внутренней сети либо добавить отдельный allowlist-маршрут для мониторинга. |

Не публиковать `/internal`, staff API, PostgreSQL, Redis, RabbitMQ и ClamAV. Для
пути Авито отключить access-log и исключить полный URI из журналов балансировщика,
WAF, APM и аналитики: URL содержит webhook-секрет.

## Подключение ВКонтакте

1. Включить сообщения у сообщества и получить токен сообщества с правами
   сообщений, получения пользователей и загрузки документов.
2. Внести три переменные `MANAGER_VK_*` в Secret, сменить `enabled` на `true`,
   перезапустить manager-server.
3. Из запущенного контейнера выполнить:

   ```bash
   bun run channels:check vk-company
   ```

4. В управлении сообществом: **API → Callback API** указать адрес
   `https://<публичный-домен>/v1/channels/vk/vk-company`, версию API `5.199`,
   секрет `MANAGER_VK_WEBHOOK_SECRET` и событие «Входящее сообщение» (`message_new`).
   Затем подтвердить адрес: ВК ожидает строку из `MANAGER_VK_CONFIRMATION`.
5. Отправить реальное сообщение и документ пользователем сообщества; из раздела
   «Клиенты» ответить текстом и файлом. Проверить обе стороны обмена.

## Подключение Авито

1. Получить `client_id`, `client_secret` и `accountId` основного корпоративного
   аккаунта. Для товаров требуется тариф «Максимальный», для услуг —
   «Расширенный» или «Максимальный» согласно Messenger API Авито.
2. Внести три переменные `MANAGER_AVITO_*` в Secret, сменить `enabled` на `true`,
   перезапустить manager-server.
3. Из запущенного контейнера выполнить:

   ```bash
   bun run channels:check avito-company
   bun run channels:subscribe avito-company
   ```

   Вторая команда использует `MANAGER_PUBLIC_URL` и регистрирует callback:
   `https://<публичный-домен>/v1/channels/avito/avito-company/<секрет>`.

4. Отправить реальное сообщение и изображение в Авито; ответить из раздела
   «Клиенты» текстом и PNG/JPEG/GIF. Убедиться, что callback возвращает 200 без
   задержки и сообщения не дублируются при повторной доставке площадки.

Авито передаёт уведомление без подписи. Защита состоит из секретного URL и
повторной загрузки сообщения авторизованным запросом к API Авито; содержимому
webhook напрямую сервис не доверяет.

## Мониторинг, эксплуатация и откат

После включения каждой площадки выполнять:

```bash
bun run channels:status
```

Настроить оповещения на:

- недоступность `/health/ready`, Redis, RabbitMQ, PostgreSQL и ClamAV;
- увеличение `failed` входящих сообщений и `failed`/`uncertain` исходящих;
- рост pending-сообщений и ошибку подключения в `channels:status`;
- ошибки `rate_limited`, `captcha_failed`, `captcha_unavailable`,
  `scanner_unavailable`, `redis_unavailable` без передачи текста сообщений,
  контактов или токенов во внешние журналы.

Для повторной обработки входящего события после устранения причины:

```bash
bun run channels:retry-inbox <connectionId> <operationUUID>
```

При инциденте отключить только проблемную запись (`enabled: false`) и перезапустить
manager-server. История обращений останется в СЭП Чате. После компрометации ключа
отозвать его у площадки, выпустить новый, заменить Secret и webhook-конфигурацию
площадки; для Авито также зарегистрировать новый callback.

## Критерий готовности

Запуск считается завершённым после прохождения всех пунктов:

- миграции manager-server и СЭП Чата применены, `/health/ready` возвращает 200;
- public HTTPS и ограничения маршрутов работают, секрет Авито не попадает в логи;
- `channels:check` прошёл для ВК и Авито;
- подтверждён callback ВК и зарегистрирована подписка Авито;
- проведены реальные проверки текста и поддерживаемого файла в обоих направлениях;
- менеджер с `chat.clients:view` видит обращение и отвечает, пользователь без права
  не видит раздел;
- мониторинг настроен, а процедура отключения/смены секретов проверена.

Подробные ограничения форматов, повторов и восстановления доставки описаны в
[CHANNELS.md](CHANNELS.md); модель защиты публичного сайта — в
[SECURITY.md](SECURITY.md).
