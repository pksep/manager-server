# Подключение платформ после виджета

Сейчас работает только widget. Ссылки на социальные сети открывают их страницы;
они не принимают переписку в manager. sep-bot-api не требуется.

Будущий адаптер платформы должен отделять её особенности от правил обращения:

| Операция | Вход / результат |
| --- | --- |
| authenticateEvent | Подпись webhook, timestamp и защита повтора; доверенный accountId и channelUserId |
| acceptMessage | channel, accountId, conversationId, externalMessageId, sentAt, текст, файлы; стабильная операция при повторе события |
| deliverMessage | inquiryId, стабильный operationId, сообщение; идентификатор платформы и подтверждение или ошибка для очереди |
| upload/download | Поток в защищённое хранилище чата, проверенный размер/MIME и принадлежность обращению; внешние URL не выдаются менеджеру как доверенные файлы |
| verifyIdentity | Тип реквизита, нормализованное значение, способ и время подтверждения; введённый пользователем текст не считается подтверждением |
| capabilities | Поддержка текста, файлов, максимальных размеров/количества, прочтений, редактирования, удаления и возможности первого сообщения |

Для widget сейчас доступны текст, прямые файлы и прочтения. Редактирование,
удаление и пересылка внешних сообщений не реализованы. Интерфейс нового раздела
должен показывать только действия, которые поддерживает подключённый канал.

Внутренний контракт будущего канала не должен вызывать гостевой API виджета:
у виджета авторизация сессией и origin, у webhook — подпись платформы. Каждый
адаптер после своей проверки вызывает общие правила создания обращения,
очереди, назначения и контактов. Назначение первого ответившего и ручной выбор
ответственного остаются одинаковыми для всех платформ.

Ключ входящей операции: channel + accountId + externalMessageId. accountId
обязателен, чтобы одинаковые идентификаторы разных подключений не столкнулись.
Повторы доставки используют исходный ключ; события собственного исходящего
сообщения обновляют подтверждение, не создают входящее сообщение.

Имя, email и телефон из неподтверждённого профиля дают кандидатов. Для общей
истории менеджера уже можно явно связать карточки с одним контактом ЕРП.
Автоматическая верификация и интерфейс исправления неверной связи — отдельные
операции с журналом, они пока не реализованы. История гостю после связи не открывается.

До реализации конкретного адаптера нужны выбранная платформа, права её API и
проверка фактических возможностей. Чат продолжает быть владельцем сообщений и
файлов, manager — владельцем обращений/доставки/связей, ЕРП — контактов и ролей.
