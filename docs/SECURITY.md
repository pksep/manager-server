# manager: защита публичного приёма

Задача и ветка: `manager`. Изменения согласованы 15.09.2026: Яндекс SmartCaptcha,
защита от массовых сессий/сообщений, проверка файлов и исправления замечаний PR.
Подтверждение телефона и email не вводится. Клиент по-прежнему объединяется только
при совпадении обоих нормализованных контактов; новая гостевая сессия не получает
старую переписку. Такое объединение не доказывает владение контактами.

## Поведение и сохранённые правила

Ранее лимит был преимущественно привязан к сессии, файлы принимались в память,
а задания выбирались таймером из БД. Теперь лимиты общие для экземпляров сервиса,
смена сессии не обнуляет бюджет IP, файл проверяется до появления в хранилище Чата,
а доставкой заданий и повторами управляет RabbitMQ.

Сохранены существующие операции создания топика, записи сообщения, приватного S3
и медиа Чата, обычные формы контактов ERP и проверка права `chat.clients:view`.
Первый ответ назначает ответственного один раз; другие менеджеры могут отвечать.
Изоляция истории и файлов посетителя проверяется по сессии, не по контактам.
События набора, прочтения и изменения клиентского топика адресованы действующим
менеджерам, а не прежним участникам комнаты.

При сквозном прогоне обнаружена конкуренция синхронизаций с размером пула БД 5:
внутренняя проверка роли брала дополнительное соединение вне уже открытой
транзакции. Проверка теперь получает существующую транзакцию и читает актуальные
разрешения без кеша; обычные проверки вне транзакции сохраняют прежнее кеширование.
Регрессия проверяет передачу соединения, отказ при отозванном праве и пять
одновременных HTTP-запросов синхронизации.

## Настройки и ограничения

| Объект | Значение по умолчанию |
| --- | --- |
| HTTP | 600 запросов/IP/мин, 10000 на сервис/мин |
| Новые сессии | 30/IP/мин, 120/IP/час, 30/подписанный браузер/час, 3000/сайт/час |
| Сообщения | 20/сессия/мин и 20/браузер/мин, 120/IP/мин, 1000/сайт/мин |
| Новые обращения | 30/IP/час, 1000/сайт/час |
| Одинаковые сообщения из разных сессий | более 10/IP/сайт/мин → 429 |
| WebSocket | 3/сессия, 30/IP, 1000 на сервис; авторизация 5 с, без heartbeat 60 с |
| Файл | максимум 20 MiB, один файл в запросе; HTTP-загрузка максимум 60 с |
| Параллельные загрузки | 2/IP, 8 на сервис |
| Объём загрузок | 100 MiB/IP/час, 1 GiB/сайт/час |
| Архив | до 1000 элементов, 100 MiB распакованных данных; без шифрования и опасных путей |

Счётчики используют атомарные операции Redis, время Redis и срок жизни записей.
IPv6 объединяется по /64, IPv4-mapped адреса нормализуются. Переданный клиентом
`X-Forwarded-For` игнорируется, если непосредственный отправитель не входит в
`MANAGER_TRUSTED_PROXIES`. Идентификаторы ключей хешируются с серверным секретом.
Подписанный `visitorToken` — дополнительный лимит браузера, не авторизация и не
источник истории. Удаление localStorage не снимает лимиты IP и сайта.

Если Redis или RabbitMQ недоступны, готовность приёма отрицательна и виджет скрыт.
Сбой проверки CAPTCHA или файла не разрешает отправку. При 429 возвращается
`Retry-After`; текст, контакты и выбранные файлы остаются для повторной попытки.

## Яндекс SmartCaptcha

На локальном стенде ключей пока нет. `MANAGER_CAPTCHA_MODE=disabled` разрешён
только при loopback HOST и loopback источниках всех сайтов. Для внешнего окружения:

```dotenv
MANAGER_CAPTCHA_MODE=adaptive
SMARTCAPTCHA_CLIENT_KEY=<клиентский ключ>
SMARTCAPTCHA_SERVER_KEY=<серверный ключ>
MANAGER_SCAN_MODE=required
```

`required` проверяет каждое первое обращение, `adaptive` — подозрительные повторы
и поток новых обращений. В обоих режимах загрузка файла требует проверки.
Скрипт Яндекса подгружается по требованию; секрет остаётся на сервере. Одноразовый
challenge связан с сайтом, origin, сетью и конкретным содержимым операции.
Сервер проверяет токен у Яндекса и требует `status=ok` с точным host (включая порт).
Пустой host, ошибка провайдера или повторный токен не дают доступ.

В разрешённые домены ключа включается домен **страницы виджета в iframe**.
Политика CSP страницы виджета должна разрешать скрипты, фреймы и соединения
SmartCaptcha согласно настройке Яндекса. Уведомление провайдера не скрывается.
Настоящая проверка в браузере с ключами остаётся обязательной перед внешним запуском.
Локальные тесты проверяют контракты и ошибки провайдера с подменёнными ответами;
это не проверка действительного токена Яндекса.

Документация: [валидация](https://yandex.cloud/ru/docs/smartcaptcha/concepts/validation),
[методы виджета](https://yandex.cloud/ru/docs/smartcaptcha/concepts/widget-methods).

## Файлы, SQL и инфраструктура

Файлы принимаются во временный каталог вне HTTP-корня, проверяются по расширению
и сигнатуре, затем потоково проверяются ClamAV и передаются штатному S3-сервису
Чата. Разрешены PDF, PNG, JPEG, GIF, WEBP, TXT, CSV, ZIP, DOCX и XLSX. HTML, SVG,
исполняемые файлы и неизвестные форматы отклоняются. Заголовок браузера MIME не
считается доказательством типа. ClamAV должен обновлять сигнатуры и быть доступен
только сервису. Ограничения распаковки дополнительно заданы в `config/clamd.conf`.

Временные файлы удаляются после запроса; оставшиеся после аварии — через сутки.
Брошенные вложения истёкшей сессии удаляются через час после её окончания, пачками
по 50. Перед удалением Чат повторно проверяет владельца и отсутствие связи с
перепиской под блокировкой. История отправленных сообщений не удаляется.

Sequelize управляет моделями и транзакциями, как в существующих сервисах.
Составной SQL с блокировками сохранён с отдельными bind-параметрами. Имена таблиц
очереди берутся из закрытого набора, колонка доступа Чата — из списка разрешённых.
HTML очищается до сохранения и повторно в клиенте. Конфигурация upstream только
серверная; пользовательский URL не превращается в адрес серверного запроса.

Runtime-пользователь БД должен иметь только SELECT/INSERT/UPDATE/DELETE и права
на последовательности. Миграции запускаются отдельно с
`MANAGER_MIGRATION_DATABASE_URL`; runtime не должен быть владельцем схемы,
superuser или иметь CREATE. В локальном Docker первоначальный администратор
нужен установщику и интеграционным тестам; его нельзя переносить в production.
Шаблон разграничения прав: `config/database-permissions.sql`.

`config/nginx.conf` — шаблон входного шлюза: ограничения частоты, соединений,
тела и времени запросов; наружу открыт только `/v1/widget/`. Нужно заменить CIDR
балансировщика, настроить TLS и разрешить backend только от шлюза. Указать этот
шлюз в `MANAGER_TRUSTED_PROXIES`; не использовать `0.0.0.0/0` или доверие ко всем.
Это шаблон, не развёрнутая защита внешнего сайта. Для объёмных DDoS необходима
защита на внешнем балансировщике/WAF. Redis, RabbitMQ, БД и ClamAV наружу не открывать;
для сетевых подключений за пределами доверенной сети использовать TLS и отдельные
учётные записи/виртуальные хосты. Ключи не включать в URL логов, браузер или Git.

## Очередь и миграции (замечания PR)

RabbitMQ содержит только ID заданий. Очереди delivery/erp durable, сообщения
persistent; ACK приходит после обработки, публикация подтверждается брокером.
На каждого потребителя prefetch=1. Отложенные повторы проходят через retry-очередь;
лимиты длины и числа попыток сохранены. В БД остаются бизнес-статусы и атомарный
журнал намерений: после commit он позволяет восстановить потерянную публикацию.
При потере ответа возможна повторная доставка, поэтому прежние ключи операций
и проверка порядка обязательны. Это не обещание «ровно одной доставки» транспорта.

Umzug использует прежний журнал `manager_schema_migrations`. Каждая команда up/down
атомарна, защищена advisory lock; `down` откатывает последнюю версию. Автоматического
DDL при запуске HTTP-сервера нет. Миграции 006/007 добавляют срок публикации и
идентификатор браузера. Откат 005 после фактического объединения нескольких сессий
может быть отклонён: нужна резервная копия, потеря разделения истории недопустима.

VK-ссылка берётся из `VK_BUSINESS_URL` ERP через защищённый
`GET /api/internal/manager/access/widget`. Пустое значение скрывает пункт;
кеш сохраняет последнее корректное значение при кратком сбое ERP. Без ERP
используется одноимённая настройка manager. Фиксированная ссылка удалена из демо.
Три локальных отладочных скрипта ERP и журнал ERROR_PREVENTION виджета исключены
из PR по замечаниям автора; локальные копии не являются частью поставки.

## Наблюдение и проверки

События rate_limited, repeated_messages, captcha_failed/unavailable,
scanner_unavailable, file_rejected, redis_unavailable и ошибки очистки пишутся
без содержимого сообщений и контактов; шумные предупреждения ограничены по времени.
Суточные счётчики Redis `<prefix>:metrics:YYYY-MM-DD` живут 7 дней. В эксплуатации
настроить уведомления по недоступности зависимостей, росту отказов и возрасту
необработанных delivery_operations/erp_sync_operations. Сами внешние уведомления
этот PR не настраивает и никому не отправляет.

`bun run test:security` создаёт отдельную временную БД и уникальные очереди/ключи.
Он проверяет полный цикл миграций, SQL/HTML, конкуренцию лимитов, новые сессии,
потерю ответа при доставке, изоляцию истории, CAPTCHA и настоящий ClamAV.
Тест EICAR использует безвредную антивирусную сигнатуру: Windows Defender может
удалить её временный файл до ClamAV (закрытый ответ 503); отдельная передача той же
сигнатуры в ClamAV проверяет обнаружение без файловой системы Windows.

`test:integration` и `test:erp` используют настоящий изолированный стенд, акторов
из `.local/erp-actors.json` и роли ERP. Временные изменения прав и полей fixture
восстанавливаются. На время этих тестов отдельный manager на 4314 нужно остановить.
Финальные результаты и коммиты указываются в отчёте проверки; старые отчёты не
подтверждают текущую версию.
