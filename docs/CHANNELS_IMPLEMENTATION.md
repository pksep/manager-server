# manager: ВК и Авито

Основание: пользователь разрешил автономно реализовать оба подключения 15.09.2026.
Ветка во всех затронутых репозиториях — `manager`. Продолжаются существующие PR:
manager-server#1 (main), chat_server#180 и chat_client#402 (canary).
Общий пакет Чата и sep-yui берутся из уже подключённых версий этой задачи.

## Поведение и инварианты

- Сообщения сайта, сообщества ВК и аккаунта Авито приходят в «Клиенты».
- Все сотрудники с действующим chat.clients:view видят переписку и могут отвечать.
- Первый ответ назначает менеджера один раз; следующие ответы не переназначают его.
- Автоматическое объединение по совпадению обоих контактов сохранено без OTP.
  При отсутствии реквизитов клиент определяется аккаунтом и ID пользователя канала.
- Общая карточка клиента не объединяет адреса доставки. Ответ получает неизменяемый
  маршрут при отправке. Новое входящее сообщение не перенаправляет уже созданный ответ.
- Новая сессия сайта не получает прежнюю историю. Чужой маршрут или вложение недоступны.
- Секреты платформ остаются в серверном окружении. Webhook подтверждается после
  сохранения входящего события; повторы не создают сообщения повторно.

## Переиспользование

InquiriesService хранит обращения и назначение, resolveCustomer сопоставляет контакты,
OperationQueue доставляет задания RabbitMQ и восстанавливает публикацию через outbox.
ChatAdapter вызывает штатный ManagerController → GroupsService / MessagesService /
ManagerStorageService. FileInspection проверяет файлы перед приватным хранилищем Чата.
StaffGuard, ManagerStorageService.assertManager и источник ERP остаются точками проверки прав.
Обычный ContentEditor и отправка сообщений Чата сохраняются; добавляется явный маршрут.

## Этапы

1. Общие маршруты переписки и миграция существующих сессий без открытия истории.
2. Серверная конфигурация нескольких аккаунтов, входящие события и адаптеры ВК/Авито.
3. Доставка ответов, вложения, подтверждения/ошибки, защита повторов и восстановления.
4. Выбор канала ответа и отображение источника/доставки в стандартном СЭП Чате.
5. Локальные контрактные, интеграционные и браузерные проверки; документация подключения.

Настоящие аккаунты проверяются только при наличии ключей и доступного HTTPS callback.
Имитация API в локальных тестах явно отделяется от проверки настоящих платформ.

## ЕРП: клиент без телефона и почты

До правки прослежен useErpContact → штатная форма contactbase → erp/sync →
ErpSyncService → ManagerContactsController/Service → managerContactSyncZod
в packages/zod-shared репозитория sep_erp_server (PR 1710, manager → canary).
Поиск по identity/contactId/managerContact во всём модуле и общем пакете показал,
что canonical sync уже проверяет выбранный контакт, права и сохраняет связь транзакционно.
Его DTO требовал реквизиты даже при явно выбранном contactId. Требование подключения
ВК/Авито подразумевает сохранение этой штатной формы для пользователя без реквизитов.
Расширяется общая схема: пустая identity разрешена только вместе с contactId.
Создание без contactId по-прежнему требует телефон или email. Права, проверка активного
контакта, ключ повтора и сохранение связи остаются в существующем сервисе.
Проверки: границы общей схемы и связь обращения без реквизитов через реальную ЕРП.
