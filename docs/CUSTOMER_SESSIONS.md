# Повторное обращение одного клиента

Задача `manager`, уточнение от 14.09.2026. Совпадение одновременно телефона и
email после нормализации использует прежнего клиента и один открытый чат.
Новая гостевая сессия не создаёт вторую строку в разделе «Клиенты». Менеджер,
примечание и контакт ЕРП сохраняются. Совпадение только одного реквизита не
объединяет карточки автоматически; разные связанные контакты ЕРП дают конфликт.

Идентификатор клиента используется для сопоставления, а не для авторизации.
У каждой гостевой сессии свой токен; все сообщения помечены сессией получателя.
HTTP-история, начальный снимок и WebSocket возвращают только её сообщения.
Одинаковый ключ отправки из двух сессий обрабатывается независимо.

Чат менеджера сохраняет обычный топик и все прежние сообщения. При доставке
нового сообщения интеграция атомарно запоминает текущую гостевую сессию в той же
транзакции. Ответ менеджера адресуется этой сессии; событие фиксирует адресата,
даже если до доставки ответа посетитель написал из другого браузера. Прочтение
старого сообщения отправляется именно в его исходную сессию. Повтор доставки
не переключает адресата назад.

Для обновления нужны миграции `005_customer_sessions.sql` в manager и
`20260914120000-manager-customer-sessions.js` в чате, затем обе новые серверные
версии. На время миграции запись старой версией manager нужно остановить:
у сообщений появляется обязательная связь с гостевой сессией. Откат требует
резервной копии; автоматическое разбиение уже объединённых чатов не выполняется.

Старые дубли не удаляются массово. Проверенные записи связываются с сохранением
старых идентификаторов, токенов, сообщений и резервной копии. Закрытая строка
дубля исключается из списка; старый публичный идентификатор обращения работает
только для уже связанной гостевой сессии и также не открывает общую историю.
