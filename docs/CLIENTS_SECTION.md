# Клиенты — уточнение задачи manager

Основание: требования пользователя 14.09.2026 к разделу «Клиенты», карточке,
множественному выбору менеджеров и примечанию. Ветки всех репозиториев: manager.

Изучено: StaffController/ErpSyncService сервиса обращений, ManagerStaffController
и стандартные GroupsService/MessagesService чата, useChatMenu/Menu/TopicList,
MobileList, Header, useUserInfoModal/UserInfoPanel/ProfileAttachmentsPanel.
В ЕРП найдены BoardUserFilter из ModalTask (AssigneesFilter) и YTextarea из
ModalContact для примечания. Сообщения/файлы идут через прежний транспорт.

Прежнее правило: assignee_id назначается первым ответом, ручной выбор имеет
приоритет. Новое требование расширяет ручной выбор до списка manager_ids.
Первый ответ заполняет список одним сотрудником; последующие ответы его не
меняют. Старый API одного ответственного продолжает работать. «Мои заявки»
означает вхождение текущего менеджера в список, «Новые» — пустой список.
Выбор менеджеров не ограничивает право остальных отвечать.

Примечание хранится в карточке обращения, не публикуется посетителю и не
перезаписывает описание контакта ЕРП. Изменения карточки сохраняются с версией:
при одновременном редактировании возвращается конфликт вместо потери записи.
Связь контактов по телефону/email, очередь ЕРП и изоляция гостевой истории
остаются в канонических серверных операциях.

Клиент использует те же топики, списки сообщений, редактор, пользовательскую
модальную панель и медиа/файлы. Внешние топики отделяются от обычного списка.
Название — имя/инициалы с телефоном; подзаголовок переписки — платформа,
подзаголовок карточки — email. Фильтры платформ: сайт, Авито, ВКонтакте.
Наличие фильтра не означает, что адаптер платформы уже подключён.

Проверки: два менеджера, автоназначение и ручной множественный выбор,
«Мои»/«Новые», сохранение примечания и конфликт версии, отзыв доступа,
создание/связь ЕРП через прежний API, обычные чаты, мобильная навигация,
файлы и отсутствие вызова телефонии для внешнего клиента.

## Реализованные поверхности

- Чат: центральный пункт «Клиенты», две группы фильтров, обычный TopicList,
  существующие сообщения и редактор, профиль клиента в Header/UserInfoPanel.
  На компьютере профиль открывается справа в прежнем chat__user-info-modal,
  на телефоне — в прежнем MobileModal. Обе группы фильтров переиспользуют
  ChatsToolbarFilters с исходной разметкой и стилями фильтров обычного чата.
  Звонки внешнему клиенту отключены, файлы показывает ProfileAttachmentsPanel.
- sep-yui: UserMultiSelect перенесён из BoardUserFilter без изменения вариантов
  default/task-card; адреса изображений теперь подготавливает потребитель.
  Добавлена предоставленная пользователем иконка 24/Headset. Компоненты Modal
  не изменены: расширение положения left удалено по уточнению пользователя.
- ЕРП: BoardUserFilter стал адаптером общего компонента. TableContacts принимает
  contactId в адресе, открывает прежний ModalContact и сохраняет прочие фильтры.
  Загрузка контакта выполняется прежним fetchOneContact/getContactById.
- manager: миграция 004, множественное назначение, внутреннее примечание,
  журнал изменений и проверка версии. Сохранение только примечания не помечает
  назначение ручным. После ручного снятия всех менеджеров автоназначение не
  включается повторно. Первичный assignee_id сохраняется, пока он есть в списке.
- Чат-сервер: защищённые access/managers/metadata, данные аватарки внешнего
  пользователя, постраничный список и восстановление ранее отозванного участия.

## Повторная выдача права

На изолированном контуре подтверждён сбой: после удаления права прежние
TopicSetting и GroupMemberRole оставались в базе с deletedAt, а повторная выдача
пыталась создать дубликаты. Теперь существующие записи восстанавливаются.
Обычный GroupsService.addMembers изучен; его административный сценарий не подходит
для доверенного снимка ролей и не изменён. Регрессия проверяет отзыв и повторную
выдачу права, доступ к обращению и ровно одну активную запись участия.

## Локальная проверка и выпуск

Ручной чат: http://127.0.0.2:4312/; второй менеджер — ?manager=2 в отдельном
браузере. Виджет: http://127.0.0.1:4310/?service=manager. Автовход, снимки прав,
базы и хранилище относятся только к локальному контуру manager.

`bun run test:clients` проверяет работающий ручной стенд: два ответа через
интерфейс, сохранение первого ответственного, файл, множественный выбор,
примечание, конфликт двух карточек, создание в изолированной ЕРП, фильтры,
мобильное открытие и размеры полей. Команды test:integration и test:erp сами
занимают 4314 и меняют тестовый снимок прав: перед ними остановить ручной
manager и локальный Vite, после — восстановить ручной стенд.

Для проверки используется локальная сборка ветки manager библиотеки. После её
сборки `bun scripts/use-local-yui.mjs <sep-yui> <chat-client> <erp-client>`
подключает dist к установленным зависимостям; Vite запускать с --force.
Служебная подстановка входа учитывает параметр ?t= после горячего обновления.

Перед выпуском требуется опубликовать новую версию sep-yui и обновить версии
и lock-файлы обоих клиентов. Установки из текущих lock-файлов этой новой
сборки не содержат. Публикация пакета и выкладка в этой доработке не выполнялись.
Иконка 24/Headset из предоставленного SVG подключена через IconNameEnum.headset.
Авито/ВКонтакте пока фильтры источника; адаптеры этих каналов не реализованы.
CHAT_ERP_URL должен указывать на интерфейс ЕРП. Локальный порт 4502 — серверный
интеграционный профиль, полного интерфейса ЕРП на ручном стенде нет.

При локальном подключении библиотеки обнаружены hardlink-файлы Bun: запись
поверх установленного файла могла менять тот же файл в кэше и соседнем стенде.
Соседняя зависимость восстановлена из опубликованной @pksep/yui@0.1.308:
все 170 файлов dist совпали с архивом npm. Скрипт use-local-yui теперь создаёт
новый файл и атомарно заменяет путь, разрывая hardlink перед обновлением.
Исходный код соседних проектов не менялся.

## Уточнение интерфейса 14.09.2026

Пользователь указал канонический ChatsToolbar-Filters вместо универсальных
кнопок sep-yui и правую стандартную модальную панель. Фильтры вынесены в общий
компонент внутри клиента чата; обычные чаты и «Клиенты» используют одну разметку
и те же стили. Счётчики и выбор обычного чата сохранены. В проверке ручного
стенда сравниваются стили активного/неактивного фильтра, проверяется иконка
и точные классы правой панели. Множественный выбор менеджеров внутри карточки
остаётся прежним компонентом из формы задачи.

После уточнения расположения заголовка и поиска «Клиенты» используют весь
ChatsToolbar с заголовком «Клиенты» и двумя рядами в слоте filters. Отдельная
вёрстка заголовка, поиска и отступов удалена. Обычные чаты сохраняют исходные
значения по умолчанию и меню создания; в клиентах создание из этой панели
выключено. На телефоне применяется тот же mobile-list-container__toolbar.

При загрузке обнаружено мигание пункта «Клиенты»: наблюдатель возвращал новый
массив при каждом обновлении объекта профиля и сбрасывал доступ даже при
неизменных id сотрудника и адресе API. Теперь эти два значения наблюдаются
отдельно. Обновление профиля сохраняет пункт; смена аккаунта/сервера сбрасывает
доступ и данные. Подтверждённый отзыв права по-прежнему скрывает раздел.

Примечание использует TextareaTypeEnum.minor, как UsersBlock-Block-3-Info-Textarea
в ЕРП. Над первым заголовком «Менеджер» и перед «Примечание» — 15 px.
Если erp_contact_id уже подтверждён, «Открыть в СЭП» доступна независимо от
фоновой проверки очереди. Кнопка открывает основной интерфейс ЕРП и его штатный
ModalContact сразу в режиме редактирования. Если связи ещё нет, прежний поиск
по email/телефону проверяет совпадения: один активный контакт открывается на
редактирование, несколько требуют выбора менеджером, отсутствие совпадений
открывает создание с заполненными именем, телефоном и email. Автоматического
создания по нажатию кнопки больше нет: запись появляется после «Создать» в ЕРП.
Отмена формы не меняет контакты и связь обращения. После сохранения штатный
POST/PUT /contacts возвращает id, а чат передаёт его прежней очереди erp/sync
для связи с обращением. Контакт не создаётся этой очередью повторно.

Это существующие MainLayout → BaseContacts → ModalContact. ManagerContactEntry
добавляет только получение начальных данных и открытие штатного окна, без своей
вёрстки карточки. Данные передаются между вкладками через postMessage с проверкой
точного origin, исходного окна, requestId и текущего сотрудника чата. Имена,
телефоны, email и токены не попадают в URL. При обновлении вкладки ЕРП входные
данные сохраняются в её sessionStorage с привязкой к пользователю. При закрытии
чата до сохранения контакт остаётся в ЕРП, а связь завершается следующим открытием
из чата и сохранением найденного контакта. Обычное открытие карточки из таблицы
по-прежнему начинает с просмотра; стили формы, валидация и API сохранения прежние.
Внутреннее примечание менеджеров не переносится в контакт ЕРП.

Адрес CHAT_ERP_URL должен быть
адресом интерфейса ЕРП. На тестовом стенде это http://127.0.0.3:4315/;
4502 обслуживает синхронизацию, 4503 — штатный API интерфейса контактов.
Оба используют существующую manager_erp_local. Включён основной router/index
клиента ЕРП с MainLayout, шапкой, меню и навигацией, без отдельного роутера страницы.
Автоматический вход относится только к тестовому окружению. VITE_CHAT_URL ЕРП
должен указывать на доверенный чат; в локальной конфигурации это 127.0.0.2:4312.

При запуске интерфейса обнаружено, что getContacts исключал контакты без компании:
условие ban=false на связи Companies превращало её в обязательную. Обращения
создаются без компании, поэтому контакты находились по id, но отсутствовали в
списке. Для выполнения требования показать созданных клиентов связь теперь
обязательна только при выбранном фильтре компании/типа. distinct сохраняет верное
число контактов при нескольких компаниях. Поиск, архив, права, создание,
редактирование, транзакции и журнал действий используют прежние реализации.
