# Фаза 2: транспорт обращений

Задача и ветки: `manager`. Состояние на 11.09.2026: готов первый сквозной
участок второй фазы, вся фаза ещё не завершена.

## Что можно проверить сейчас

Посетитель открывает виджет, оставляет контакты и отправляет текст или файл.
Сервис сохраняет обращение и очередь доставки в своей PostgreSQL. Сервер чата
создаёт обычную группу через GroupsService и хранит сообщения через
MessagesService, вложения через Media и S3Service. Менеджер отвечает в тот же
топик; посетитель получает ответ и отметки прочтения по WebSocket.

Первый ответ назначает ответственного. Другой менеджер может ответить, не
меняя его. Ручное назначение сохраняется даже при запоздалом получении первого
ответа. Источник сайта фиксируется серверной конфигурацией, query/hash страницы
не сохраняются. Новая гостевая сессия не получает прежние обращения.

Повторы защищены уникальными ограничениями и блокировками базы. На стороне
чата сообщение, его Media, подтверждение операции и событие фиксируются одной
транзакцией. На стороне manager приём сообщения и операция доставки также
атомарны. После потерянного ответа либо перезапуска повтор использует прежний
идентификатор; второй топик/сообщение не создаётся.

## Фактические контракты

| Участок | Контракт |
| --- | --- |
| Виджет → manager | `/v1/widget/session`, `/inquiries`, `/inquiries/:id/messages`, `/attachments`, `/attachments/:id` |
| Обновления виджета | `/v1/widget/events`; первое сообщение `authenticate`, затем `ready`, `message`, `ping`/`pong` |
| manager → чат | `/api/internal/manager/inquiries/:id/messages`, `/events?after=…`, `/attachments`, `/attachments/:id`, `/managers/:id/access` |
| Сотрудник → чат | `/api/manager/inquiries`, `/inquiries/:id`, `/inquiries/:id/messages`, `/attachments`, `/assignee`, `/retry` |
| Чат → manager | `/internal/staff/inquiries`, `/inquiries/:id`, `/assignee`, `/retry`; заголовки `x-manager-key`, `x-actor-id` |
| Снимок полномочий | `PUT /api/internal/manager-access/snapshot`; отдельный `x-manager-access-key`, монотонная revision, срок не более 15 минут |

Последние три кратких маршрута каждого раздела являются дочерними относительно
`/inquiries/:id`. Схемы публичного протокола и проверка событий находятся в
`src/contracts.ts`; сервер чата проверяет собственный вход через Zod. Совместимость
между двумя репозиториями проверяет настоящий HTTP-тест, включая разбор каждого
события схемой manager. Новая внутренняя версия — `1`.

Событие идентифицируется парой `(inquiryId, sequence)`, где inquiryId уже задан
маршрутом. `messageId` относится к каноническому сообщению чата. Для исходящего
сообщения `operationId` связывает его с сохранённым сообщением manager.
Типы событий этого участка — `message` и `read`. Курсор продвигается только
при непрерывной последовательности. Собственные исходящие события обновляют
подтверждение, не создавая входящее сообщение.

Получение ответов пока выполнено опросом долговечного журнала чата. RabbitMQ
сохраняет существующую работу чата, но новая доставка не полагается на его
недолговечное уведомление. Интервал задаёт `MANAGER_WORKER_MS`; один проход
обрабатывает до 20 отправок и 50 обращений, страницы чередуются. Доставка
повторяется до 10 попыток с задержкой до 60 секунд. После этого видна ошибка
в карточке; сотрудник может повторить доставку с тем же ключом.

## Доступ и файлы

Гостевой токен хранится только как SHA-256 и ограничен сроком, сайтом и origin
виджета. Отдельно проверяется origin исходного сайта. Внешний автор чата имеет
`is_external=true`, исключён из справочника сотрудников и вариантов входа;
обычный вход и сокетная авторизация для него запрещены.

Право раздела проверяется при чтении, ответе, назначении и скачивании. Просроченный
либо отсутствующий снимок закрывает менеджерский доступ. Снимок обновляет штатные
TopicSetting/GroupMemberRole. Отозванный пользователь исключается из топиков,
списков и повторной синхронизации. Полные сообщения внешних обращений рассылаются
только личным комнатам менеджеров с действующим правом.

Файлы хранятся в существующем зашифрованном S3 чата, в области `manager-private/`.
Посетитель использует attachmentId своей сессии; произвольный objectPath от него
не принимается. Общая выдача `/api/media/object/…` тоже проверяет право сотрудника
и принадлежность файлу обращения. Файлы выдаются как скачивание, с `no-store`
и `nosniff`. Клиент чата загружает их с авторизацией и не кладёт в общий IndexedDB
кеш. Служебные ключи скрыты в HTTP-журнале.

Сейчас загрузка целого файла ограничена конфигурацией сайта, максимумом 100 MiB
на сервере и числом вложений; локально — 10 MiB и 5 файлов. Повтор загрузки с
тем же ключом возвращает тот же файл, а другое содержимое отклоняется. Русские
имена сохраняются. Ответы с файлами используют специальный загрузчик обращения
через `/api/manager/inquiries/:id/attachments`.

## Что ещё не завершено

- Точный поиск контакта в ЕРП, разбор конфликтов, связь с существующим контактом
  и повторяемое «Добавить в СЭП» через ContactService/ActionsService. Таблица
  `erp_sync_operations` подготовлена, выполняющего её обработчика ещё нет.
- Подтверждение личности, ручное связывание клиентов разных каналов и общая
  история связанного клиента. Сейчас совпадения телефона/email показываются
  кандидатами и не объединяются автоматически.
- Производитель снимка прав из ЕРП, ключ права и редактор ролей; это зависимость
  этапа 3. На изолированном стенде снимок создают только тестовые сценарии.
- Новый раздел и действия в интерфейсе чата, подключение его редактора к
  защищённому загрузчику. Отправка старым общим загрузчиком в специальный топик
  явно отклоняется; обычные чаты продолжают работать как раньше.
- Очистка несвязанных загрузок, возобновляемая передача, защищённые превью
  изображений/видео, политика MIME и производственные квоты.
- Полная постраничная история в интерфейсах, обслуживание срока хранения,
  метрики очереди, нагрузочные проверки и проверка нескольких экземпляров.
  Сейчас снимок виджета содержит последние 500 сообщений текущей сессии;
  HTTP-история доступна страницами по 100, список обращений ограничен 100.
- Изменение, удаление и пересылка сообщений внешнего обращения. Сейчас эти
  операции отклоняются явно, до добавления соответствующих событий в виджет.
- Реальные адаптеры других платформ. Текущий вход принимает только `widget`;
  ссылки на социальные сети не выданы за интеграцию переписки.

## Проверки

`bun run test:integration` использует отдельные базы `manager_local` и
`manager_chat_local`, настоящий сервер СЭП Чата, Redis, RabbitMQ и S3. Внешние
производственные подключения тест запрещает. Семь сценариев проверяют:
источник/авторизацию; пять одновременных повторов; ответы/прочтения/назначение;
файлы в обе стороны и чужой доступ; новую сессию при совпавших контактах;
потерю подтверждения и перезапуск; отзыв права и запрет входа посетителя.

`bun run test:browser` запускает Chrome: контактная форма → настоящее обращение →
ответ из чата → файл без модального окна → полное скрытие при остановке manager.
Снимок проверки: `.local/widget-real-chat.png`. Браузерный драйвер запускается
через Node: в этом Windows-окружении запуск Playwright напрямую через Bun зависал
на создании страницы. Сам manager отдельно проверен при выполнении в Bun.

Дополнительно пройдены сборки manager, чата и виджета, проверка типов клиента
чата и 70 существующих тестов сообщений, групп, топиков, приглашений и файлов.
Это проверка первого участка второй фазы, а не приёмка всей интеграции с ЕРП
или разрешение выпускать её на производственный сайт.
