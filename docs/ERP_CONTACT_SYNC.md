# Обновление контакта из СЭП

## Сценарий

Посетитель Telegram или MAX может написать без телефона и почты. Оператор открывает контакт кнопкой из Чата, сохраняет его в штатной форме СЭП. Manager получает актуальные реквизиты с сервера СЭП и обновляет карточки связанных обращений. Повторное редактирование также запускает обновление, даже если номер контакта не изменился.

Имя автора во внешней платформе сохраняется. Телефон и email берутся из СЭП; удаление реквизита в СЭП очищает соответствующее значение и поисковое совпадение в Manager. При нескольких телефонах или адресах карточка показывает первое непустое значение, поиск учитывает все корректные значения.

## Дубли и границы доступа

- Обращения, связанные оператором с одним контактом СЭП, получают одинаковые актуальные реквизиты и общую операторскую историю.
- Отдельные диалоги Telegram/MAX, адресаты ответов, назначения и сообщения не переносятся и не удаляются.
- Телефон или почта по отдельности не объединяют людей автоматически. Существующий поиск по двум реквизитам сохраняется; разные контакты СЭП с одинаковыми реквизитами требуют разрешения конфликта.
- Совпадение имени ничего не доказывает. Архивные контакты и смена уже установленной связи отклоняются.
- Сессия посетителя не получает историю других сессий. Общая история доступна только сотрудникам с разрешением раздела.
- Физическое слияние разных карточек внутри СЭП не выполняется. Для общей истории оператор выбирает один существующий контакт.

## Реализация и причина изменения

Основание: запрос пользователя о возврате реквизитов из СЭП и подтверждение сохранения отдельных диалогов.

Переиспользованы `ManagerContactsService.sync`, журнал `erp_sync_operations`, очередь `erp`, поиск `findIdentityCandidates`, `resolveCustomer`, штатная история обращений и обмен сообщениями с окном СЭП. Нового обхода авторизации или сохранения из браузерного профиля нет.

Старое поведение сохраняло только `erp_contact_id`. Завершённая операция навсегда занимала уникальный индекс клиента, а Чат пропускал сохранение уже связанного контакта. Теперь завершённые квитанции сохраняются в журнале, но не блокируют новую операцию. Повтор одного ключа остаётся идемпотентным. Новый ключ при незавершённой операции получает конфликт, а не ложный успех старого обновления.

СЭП перечитывает актуальный снимок также при повторе квитанции. В Manager обновление всех карточек одного контакта и его поисковых реквизитов атомарно; версия СЭП защищает от запоздавшего снимка. Переписка и маршруты не изменяются.

## Порядок выкладки

1. Обновить `sep_erp_server`: ответ штатной синхронизации дополнен снимком контакта. Старый Manager совместим с расширенным ответом. Общая библиотека собирается внутри ERP; отдельный выпуск пакета для этой доработки не нужен.
2. Применить штатным механизмом Manager миграцию `011_erp_contact_refresh.sql`. Рабочий сервер без неё не запускает ERP-синхронизацию.
3. Обновить `manager-server`.
4. Обновить `chat_client`.
5. Из Чата открыть существующий контакт, изменить телефон/email, сохранить. Проверить карточки обоих каналов и общую историю, затем убедиться, что ответ по-прежнему уходит в исходный канал.

Новые секреты не требуются. Изменения, сделанные прямо в отдельной вкладке СЭП без открытия контакта из Чата, не рассылаются автоматически: для обновления нужно открыть и сохранить контакт через Чат. Старые связанные карточки обновятся при следующем таком сохранении; массовой перезаписи production-данных нет.

Откат миграции после нескольких завершённых синхронизаций одного клиента намеренно запрещён: старый уникальный индекс несовместим с сохранённым журналом. Нельзя удалять квитанции ради отката.

## Проверки

- `bun run test`: полный модульный набор Manager.
- `bun run test:erp-refresh`: настоящая временная PostgreSQL в собственном Docker-контейнере; ERP-граница подменена локальным HTTP-сервером. Проверяются обновление, повтор, конфликт, два канала, версии, rollback, права, ошибки связи и миграция.
- `bun run test:delivery-recovery`, `bun run test:bots`, `bun run test:avito`: изолированные регрессии доставки.
- ERP: `manager-contact-refresh.spec.ts`, проверки текущих прав и контракта внешних каналов; полный модульный набор отдельно.
- Чат: `erpContactSync.test.ts` исполняет фактический обработчик с контролируемыми зависимостями; проверяет новую и существующую связь, ожидание конкретной операции, чужое окно и смену аккаунта.

Это не заменяет проверку сохранения в настоящем интерфейсе СЭП на совместном стенде. Production не менялся.
