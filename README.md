# manager-server

Сервис обращений между виджетом и СЭП Чатом. Принимает текст и файлы,
сохраняет обращения, доставляет сообщения в топики чата и возвращает ответы
менеджеров в виджет. Назначает первого ответившего и поддерживает ручной выбор.

Задача и рабочая ветка: **manager**.
Редакция от **15.09.2026**. Реализованы раздел «Клиенты» Чата, выдача полного
доступа через роли ERP, штатные формы контактов, общая история менеджеров и
отдельная история каждой гостевой сессии. Доставка заданий использует RabbitMQ,
хранение — Sequelize/PostgreSQL. Защита и условия внешнего запуска описаны в
[SECURITY.md](docs/SECURITY.md). Ключи Яндекс SmartCaptcha пока не добавлены.

Требования к виджету находятся в `pksep/manager-client`,
файл `docs/WIDGET_SPEC.md`. В соседнем локальном клоне это
[WIDGET_SPEC.md](../manager-client/docs/WIDGET_SPEC.md).

Основная схема: виджет/каналы ↔ `manager-server` ↔ сервер СЭП Чата;
`manager-server` ↔ ЕРП. `sep-bot-api` не участвует.

Для продолжения задачи дополнять эти документы и использовать ту же ветку
`manager` в каждом затронутом репозитории. Для чата основа будущих PR — `canary`.
В новых репозиториях `manager-client` и `manager-server` первая опубликованная
ветка — `manager`; открытые PR продолжаются в ней. Пакеты пока не публикуются.

## Локальный запуск

Нужны Bun, Docker и Node. В текущем рабочем пространстве используется сервер
чата из `../.worktrees/manager-chat-server`, также в ветке `manager`.
Сначала в его каталоге установить зависимости и собрать код:

```powershell
bun install --frozen-lockfile
bun run build:lib
bun run build
```

В каталоге `manager-server`, при первом запуске:

```powershell
bun install --frozen-lockfile
bun run local:setup
bun run local:infra
bun run local:chat
bun --env-file=.env.local run migrate
```

`local:setup` создаёт `.env.local` со случайными локальными ключами и сохраняет
существующий файл без перезаписи. `local:chat` принимает путь к другому клону
чата дополнительным аргументом. Базы, контейнеры и порты изолированы от прочих
проектов: PostgreSQL 56441, Redis 56394 (manager — DB 14), RabbitMQ 55675
(manager — vhost `manager-service`), S3 59008/59009, ClamAV 53310.
Секреты остаются в игнорируемых локальных файлах.

При обновлении уже существующего RabbitMQ создать vhost один раз:
`docker exec sep-manager-local-rabbitmq-1 rabbitmqctl add_vhost manager-service`,
затем выдать локальному пользователю права:
`docker exec sep-manager-local-rabbitmq-1 rabbitmqctl set_permissions -p manager-service manager-local ".*" ".*" ".*"`.
Для нового volume vhost создаётся настройкой compose. Дождаться готовности
ClamAV после первоначального скачивания сигнатур. `migrate:up`, `migrate:down`,
`migrate:status` используют штатные парные миграции; HTTP-сервер сам DDL не выполняет.

В каталоге сервера чата:

```powershell
bun run manager:local:bootstrap
bun run manager:local:start
```

`bootstrap` разрешён только для изолированной базы `manager_chat_local`.
На новой базе создаётся текущая схема моделей чата как исходная, затем
применяется миграция manager и проверяется отсутствие ожидающих миграций.
Для существующего производственного чата используется обычный процесс миграций
репозитория, а не этот локальный помощник.

В другом терминале, из `manager-server`:

```powershell
bun run local:start
```

Сервис обращений доступен на `http://127.0.0.1:4314`, чат — на
`http://127.0.0.1:4501/api`. Проверка готовности: `/health/ready` у manager.
В запущенном стенде виджета открыть
`http://127.0.0.1:4310/?service=manager`. Обычный адрес `/` продолжает использовать
демосервис первой фазы. Порядок запуска самого виджета — в README manager-client.

## Проверки

```powershell
bun run test
bun run typecheck
bun run test:integration
bun run test:erp
bun run test:security
bun run test:browser
```

Интеграционные и браузерная проверки сами запускают/останавливают manager
на 4314: перед ними остановить отдельный `local:start`. Сервер чата и контейнеры
должны работать; для браузерной проверки нужен также стенд виджета на 4310 и Chrome.
Сквозные тесты используют акторов из `.local/erp-actors.json` и действующие роли
настоящей тестовой ERP. Поставщик прав настроен в Чате; временные изменения
прав восстанавливаются после теста. `test:security` работает отдельно на 4324/4504
с временной БД и уникальными очередями и требует поднятых контейнеров.
